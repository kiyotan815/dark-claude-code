# Codex Spec — Codex 向け設計書の作成

Claude（司令塔・1M コンテキスト）が、依存関係を読み解いた上で **Codex がそのまま実装に着手できる設計書**を書くためのワークフロー。ここで書いた設計書は [[codex-delegate]] / `/dcc:codex-impl` の入力になる。設計書のユニット構造が、そのまま委譲単位に 1:1 で対応するよう書く。

## このスキルの狙い

設計書の品質が委譲の成否を決める。曖昧な設計書は Codex を迷走させ、監査で何度も突き返す羽目になる。逆に「成果物・受け入れ条件・境界」が各ユニットに明記されていれば、`/dcc:codex-impl` は分割し直す必要なく各ユニットを委譲するだけで回る。

## 設計フェーズでやること

1. **依存関係を読む** — 既存コードの構造・影響範囲を把握（Claude の 1M コンテキストの強み）
2. **契約を固める** — インターフェース、型、スキーマ、API の入出力など、ユニット間の境界面を先に確定する（並列実装が破綻しないため）
3. **独立した実装ユニットに分割** — ファイルが競合しない単位に切る。並列可否は「触るファイルが重ならないか」で判定する
4. **設計書に落とす**（下記テンプレート）

## 書くこと / 書かないこと

| 書く（設計＝Claude の領分） | 書かない（実装＝Codex の領分） |
|---|---|
| アーキテクチャ、責務分割、データフロー | 関数の中身・行レベルの実装 |
| インターフェース / 型 / スキーマ（契約） | アルゴリズムの逐次手順 |
| ユニット分割と依存関係 | 過度な実装指示（Codex の自由度を奪わない） |
| 受け入れ条件（テストコマンドと期待結果） | |

契約（型・スキーマ・API 定義）は書く、実装詳細は書かない。ここを取り違えると Codex の裁量が消えるか、逆に破綻する。

## 設計書テンプレート

```markdown
# <機能名> 設計書

## 概要 / 背景
<何を、なぜ。1〜3段落>

## 全体設計
<アーキテクチャ、責務分割、データフロー。図や箇条書きで>

## 契約（ユニット間の境界面）
<共有される型・インターフェース・スキーマ・API 入出力。ここが並列実装の前提になる>

## 実装ユニット

### U1: <ユニット名>
- **成果物**: <1つに絞った完成状態>
- **対象ファイル**: <触ってよいファイル/ディレクトリ。ファイル内の一部なら「route.ts の DELETE handler のみ」のように範囲を書く>
- **触らない**: <変更してはいけない範囲。他ユニットの担当ファイル、AGENTS.md、設定ファイルなど>
- **テスト**: <このユニット専用のテストファイルと実行コマンド。フルスイートは指定しない>
- **受け入れ条件**: `<テストコマンド>` が通る（<期待結果>）。必要なら grep 検査（旧パターン 0 件 / 必須パターンが全呼び出し箇所に存在）、「tsc はスコープ内 0 エラー」、「AGENTS.md 未変更」を加える
- **依存**: なし（または U2 完了後）

### U2: ...
（同じ構造で繰り返し）

## 並列マップ
<どのユニットが同時実行可能か。ファイル競合しない組を明記>
例: U1 と U2 は並列可（対象ファイル重複なし）／U3 は U1 完了後

## 変更履歴
<委譲中に要件が変わったら、日付・ユーザーの発言・変更理由・影響ユニットをここに追記する>
```

## 出力方法

- 原則 `docs/` 配下にファイルとして書き出す（`/dcc:codex-impl <path>` で渡せるように）。プロジェクトに docs 慣習があればそれに従う
- **委譲前にベースブランチへ commit する** — worktree 並列実装では各 worktree から設計書を参照するため
- 設計書を書いたら、レビューを促し、`/dcc:codex-impl <設計書パス>` を次アクションとして提示する
- 設計が曖昧・要件不足のまま書き進めない。不明点は先にユーザーに確認する
- 委譲中に要件変更が入ったら、コードより先に設計書の該当節と変更履歴を更新する。再委譲プロンプトでは「設計書の◯◯節の更新済み記述に従う」と節を指定する

## チェックリスト（設計書を出す前に）

- [ ] 各ユニットの成果物が1つに絞られているか
- [ ] 各ユニットにユニット専用のテストファイルと受け入れ条件（テストコマンド＋期待結果）があるか
- [ ] 対象ファイルと触らない範囲が書かれているか（ファイル内の一部なら範囲まで）
- [ ] 並列可能なユニットが明示されているか（ファイル競合の確認済み）
- [ ] 実装詳細を書きすぎていないか（契約は書く、中身は書かない）
